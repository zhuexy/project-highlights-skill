# 亮点发现与深挖

## 候选发现

先建立小型项目地图：业务目标、模块边界、入口、存储和外部依赖、主要链路。区分依赖声明与实际调用；优先沿入口追踪，避免罗列中间件。

候选按“技术亮点”“业务亮点”或“复合亮点”标记。技术亮点回答系统能力、技术约束和实现效果；业务亮点回答业务目标、规则、决策和可扩展能力。以下类别是检索线索，仅检查与项目有关的部分：

| 方向 | 入口线索 | 判断价值的问题 |
| --- | --- | --- |
| 数据一致性 | 事务边界、状态更新、缓存更新、跨服务动作 | 一次业务操作涉及哪些资源？部分失败如何处理？ |
| 并发与幂等 | 回调、消费、库存、重复提交、唯一约束 | 重复或并行执行时具体会怎样？机制的范围与前提是什么？ |
| 性能 | 查询、执行计划、批处理、缓存、调用链 | 有没有真实瓶颈？改动针对什么数据与负载条件？ |
| 异步可靠性 | 消息发送与消费、任务、重试、补偿 | 失败在哪一层被发现？哪些动作可能重复、丢失或无法恢复？ |
| 业务建模 | 状态转换、审批、价格、结算、权限规则 | 哪些业务约束复杂？实现如何组织并验证它们？ |
| 批量数据处理 | 导入导出、扫描、分页、分片任务 | 内存和处理量如何控制？中断、续跑和部分失败如何处理？ |
| 可扩展性 | 多渠道、策略、配置、插件 | 新增一种实际业务需要改哪些地方？复杂度是否值得？ |
| 工程效率 | 测试、诊断、脚本、可观测性 | 谁减少了什么重复工作？交付结果或效果如何确认？ |

业务方向也可从营销实验、用户分群、权益策略、流程转化、成本约束、模块扩展和业务规则演进中发现。比如代码若支持多种回归优惠券周期，可将“如何选择 7/14/30 天”作为业务问题；只有实验记录或用户提供的可信材料能证明 14 天最优。没有材料时，应将实验设计写成建议或待验证假设，不得补写成已完成实验。

进一步查看反复出现的防御逻辑、相关测试和曾反复修复的模块，必要时追溯相关历史。不要把提交数量等同于价值，也不要把代码作者等同于设计者。

### 排序原则

技术候选与业务候选分别排序，再给出综合推荐；用户提供岗位目标时据此调整。给具体理由即可，不制造精确评分：

1. 是否对应真实业务约束，问题能否一句话说清？
2. 是否存在具体技术难点、边界条件和方案取舍？
3. 能否从调用链讲到失败、恢复与代价，形成完整技术故事？
4. 是否有实现、测试、历史或运行证据支持？

技术候选重点比较机制、约束、取舍和验证；业务候选重点比较目标、决策依据、业务规则和可观察结果。两类都考虑价值、可讲性及证据强度；证据待补不等于没有研究价值，但不得把推测写成结果。每个候选直接给出简版项目 Owner 视角 STAR，无需等待用户选择后才输出候选素材。

### 候选 STAR

每项候选均输出 S/T/A/R：S 描述代码或项目材料可支持的场景；T 写项目要达成的目标，若目标只能从设计推断则标为“Owner 视角重构”；A 仅写可观察到的实现与机制，并把决策动机标为推断；R 写已证实的交付、测试或运行结果。每个缺证主张先标“待验证”，紧接着给出匹配该主张的实验/验证建议，帮助用户获得量化结果或机制证据；不得虚构实验结论、收益或个人行动。

## 深挖与核验

以一个具体输入或事件作为起点，追踪到最终持久化及对外结果。对关键步骤记录调用位置、条件、状态变更和失败后的可见状态。

### 机制核验

- 找到真正约束结果的代码或数据规则，避免只引用接口定义、注解、设计文档或包装类。
- 并发问题按执行先后顺序推演；查明判断与变更是否处在相同保护范围，保护范围覆盖哪些执行主体和资源。
- 事务、锁、缓存、消息等机制分别核实作用范围、持有或生效条件、释放或结束位置；不要从一个机制推导整个系统的保证。
- 重试场景追踪重试对象、触发条件、状态记录和终止处理；分别观察失败发生在动作之前、之后和反馈期间的结果。
- 状态流转检查合法前置状态、更新条件和拒绝路径；扩展性检查一个具体新增需求将改动哪些文件。
- 缺少运行条件时明确静态分析的边界。推演出来的风险是待验证假设，实际失败需要复现或记录支持。

### 取舍与结果

选择与问题真正相关的替代方案做比较，不强行凑固定数量。区分代码可见的设计事实、作者留下的理由和分析者推测。

结果记录至少区分：代码已存在、测试定义存在、测试实际通过、已验收或部署、生产观察、实验结论有记录。测试文件存在不自动等于测试通过，部署不自动等于收益已验证。

涉及量化对比时核对指标定义、环境、数据量、负载、版本、测量方式和可比性。仅保留能由材料支持的条件，不要求用户编造缺失项。局部基准结果不扩展为全链路或生产收益。

### 最小补证方案

只为当前关键缺口给最小且具体的方案。每个方案包含：

- **待验证主张与假设**：明确什么结果会支持或推翻该说法。
- **环境、样本与基线/对照**：说明版本、数据/流量、分组方式和公平比较条件；样本量或周期应按基线波动、最小有意义差异、风险与可用流量估算，信息不足时说明缺什么。
- **步骤与指标**：给可照做的操作，定义主指标、统计口径和必要的护栏指标，并说明如何记录结果。
- **判定与局限**：解释结果如何支持结论、可能的混杂因素、适用范围和风险。方案标为“建议，尚未执行”，不虚构阈值、显著性或结论。

按主张类型选择方法：

- **性能/容量**：在相同版本条件、硬件、数据集和请求分布下，对比变更前后或候选实现；预热后重复运行，记录吞吐、延迟分位数、错误率及资源消耗。按被测对象给出可执行工具建议和配置，不只泛称“压测”：
  - HTTP/API QPS：可用 JMeter（HTTP Request、Thread Group、Ramp-up、持续时间、请求参数化；用 Summary/Aggregate Report 或 Backend Listener 导出吞吐、p95/p99、错误率），也可按团队现有工具选 k6 或 wrk。逐步增加并发并保持代表性请求比例，先预热，再多轮运行；同时监控服务端 CPU/内存、连接池、数据库和下游依赖，检查压测机自身是否成为瓶颈。
  - JVM 方法级耗时/吞吐：优先考虑 JMH，设置 warmup、measurement、fork 和代表性输入，避免用简单循环或单次计时得出结论。
  - 数据库查询：在隔离环境准备有代表性的数据量和索引，结合 EXPLAIN/执行计划与客户端压测；记录扫描行数、耗时分位数、吞吐及数据库资源，并保持缓存冷热条件可比。
  - 比较前后版本时固定硬件、配置、数据、请求分布和下游依赖；标明工具版本、并发模型、测试时长与运行次数。报告吞吐（RPS/QPS）时同时报告延迟分位数和错误率，避免把超时/失败请求从分母中静默排除。仅在隔离或获准的性能环境执行，不对生产系统直接施压。
- **业务策略/转化**：优先随机 A/B，定义实验单位与分流，避免同一用户跨组；预先指定一个主要指标（如目标期留存或增量转化）及成本、投诉、退款等护栏指标，检查样本比例异常和分群偏差。按基线和最小有意义差异估算样本与周期；若流量不足，考虑历史回放、匹配对照或分阶段上线，并明确因果结论较弱。
- **正确性/可靠性**：在隔离环境用可重复输入覆盖正常、边界、并发、重复和部分失败；检查状态、数据约束、幂等结果、恢复时间或失败率，保存测试日志与版本。
- **可扩展性/工程效率**：选一个真实新增需求作为任务，用相同验收条件比较实现前后的改动范围、文件/模块数、开发步骤或交付时间；记录实际操作，避免把设计预期说成已节省的人力。

例如回归优惠券周期有 7/14/30 天候选时，建议明确随机化单位和资格条件，按用户随机分组并控制优惠券面额、渠道和发送时机；以预先定义的回归/留存增量为主指标，同时监控核销成本、毛利和退订/投诉。根据历史基线估算样本与观察周期，检查组间可比性后再比较置信区间或预设决策规则。若不能随机分组，可用历史队列或准实验，但要说明选择偏差，不能直接称为 A/B 结论。

例如，分析重复回调时，可以建议在隔离测试环境比较顺序重复、并行重复和部分失败后的状态，记录重复副作用数、最终状态与恢复时间；具体操作必须基于项目现有入口与条件，不凭空宣称某机制已经成立。只给与当前缺口相关的方案，不自动编写测试、改业务代码、跑负载或连接外部服务。

# 亮点发现与深挖

## 候选发现

先建立小型项目地图：业务目标、模块边界、入口、存储和外部依赖、主要链路。区分依赖声明与实际调用；优先沿入口追踪，避免罗列中间件。

以下类别是检索线索，仅检查与项目有关的部分：

| 方向 | 入口线索 | 判断价值的问题 |
| --- | --- | --- |
| 数据一致性 | 事务边界、状态更新、缓存更新、跨服务动作 | 一次业务操作涉及哪些资源？部分失败如何处理？ |
| 并发与幂等 | 回调、消费、库存、重复提交、唯一约束 | 重复或并行执行时具体会怎样？机制的范围与前提是什么？ |
| 性能 | 查询、执行计划、批处理、缓存、调用链 | 有没有真实瓶颈？改动针对什么数据与负载条件？ |
| 异步可靠性 | 消息发送与消费、任务、重试、补偿 | 失败在哪一层被发现？哪些动作可能重复、丢失或无法恢复？ |
| 业务建模 | 状态转换、审批、价格、结算、权限规则 | 哪些业务约束复杂？实现如何组织并验证它们？ |
| 批量数据处理 | 导入导出、扫描、分页、分片任务 | 内存和处理量如何控制？中断、续跑和部分失败如何处理？ |
| 可扩展性 | 多渠道、策略、配置、插件 | 新增一种实际业务需要改哪些地方？复杂度是否值得？ |
| 工程效率 | 测试、诊断、脚本、可观测性 | 谁减少了什么重复工作？交付结果或效果如何确认？ |

进一步查看反复出现的防御逻辑、相关测试和曾反复修复的模块，必要时追溯相关历史。不要把提交数量等同于价值，也不要把代码作者等同于设计者。

### 排序原则

优先比较以下问题，给具体理由即可，不制造精确评分：

1. 是否对应真实业务约束，问题能否一句话说清？
2. 是否存在具体技术难点、边界条件和方案取舍？
3. 能否从调用链讲到失败、恢复与代价，形成完整技术故事？
4. 是否有实现、测试、历史或运行证据支持？

技术深度与可讲性是主排序，证据强度决定结论置信度；证据待补不等于没有研究价值。明确推荐先深挖哪些及原因，最终由用户选择。

## 深挖与核验

以一个具体输入或事件作为起点，追踪到最终持久化及对外结果。对关键步骤记录调用位置、条件、状态变更和失败后的可见状态。

### 机制核验

- 找到真正约束结果的代码或数据规则，避免只引用接口定义、注解、设计文档或包装类。
- 并发问题按执行先后顺序推演；查明判断与变更是否处在相同保护范围，保护范围覆盖哪些执行主体和资源。
- 事务、锁、缓存、消息等机制分别核实作用范围、持有或生效条件、释放或结束位置；不要从一个机制推导整个系统的保证。
- 重试场景追踪重试对象、触发条件、状态记录和终止处理；分别观察失败发生在动作之前、之后和反馈期间的结果。
- 状态流转检查合法前置状态、更新条件和拒绝路径；扩展性检查一个具体新增需求将改动哪些文件。
- 缺少运行条件时明确静态分析的边界。推演出来的风险是待验证假设，实际失败需要复现或记录支持。

### 取舍与结果

选择与问题真正相关的替代方案做比较，不强行凑固定数量。区分代码可见的设计事实、作者留下的理由和分析者推测。

结果记录至少区分：代码已存在、用户已实现、已有测试覆盖、实际测试通过、已验收或部署、生产观察。测试文件存在不自动等于测试通过，部署不自动等于收益已验证。

涉及量化对比时核对指标定义、环境、数据量、负载、版本、测量方式和可比性。仅保留能由材料支持的条件，不要求用户编造缺失项。局部基准结果不扩展为全链路或生产收益。

### 最小补证方案

只为当前关键缺口给方案，包括：验证假设、所需环境、输入、操作、预期观察和局限。明确待执行，不自动编写测试、改业务代码或实施压测。

例如，分析重复回调时，可以建议在隔离测试环境比较顺序重复、并行重复和部分失败后的状态；具体操作必须基于项目现有入口与条件，不凭空宣称某机制已经成立。

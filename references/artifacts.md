# 持久化材料约定

## 文件组织

默认把材料存放在目标仓库之外的用户级 Codex 数据目录：优先 `$CODEX_HOME/project-highlights/<project-id>/`，未设置 `CODEX_HOME` 时使用 `$HOME/.codex/project-highlights/<project-id>/`；Windows 使用用户 profile 下的 `.codex`。

稳定的 `project-id` 使用 `<repo-slug>-<hash>`：`repo-slug` 用于识别项目，`hash` 是规范化项目身份字符串的 SHA-256 前 12 位。身份字符串优先取 Git remote；GitHub 的 SSH 与 HTTPS 形式需归一成相同的 `github.com/owner/repo`，并去除 `.git` 后缀与尾部斜线。其他 remote 统一主机名大小写并去除 `.git` 后缀与尾部斜线。没有 remote 时，使用规范化仓库根目录的绝对路径；Windows 路径比较时忽略大小写并统一分隔符。索引记录该身份字符串、标识和来源。

按需要创建以下文件：

```text
<user-codex-home>/project-highlights/<project-id>/
  index.md
  H01-payment-callback/
    analysis.md
    interview.md
    resume.md
```

上面是组织示例，目录名要与实际候选对应。阶段一只创建或更新索引；选定亮点后才创建分析目录；开始访谈和生成素材时再分别建立后续文件。不要提前创建空文件或虚构示例亮点。用户明确指定其他输出目录时遵从。

索引至少记录规范化仓库根路径、Git remote（若有）、规范化项目身份字符串、项目标识和标识来源。续接时用相同规则重算 ID；remote 改变但仓库根路径一致时，检查已有索引中的根路径以找到并续接旧材料，而不是另起一份。不要仅按仓库名匹配。

旧版本可能在仓库根目录创建了 `project-highlights/`。可以读取旧索引以续接上下文，但后续写入默认的用户级目录；不自动删除、覆盖或移动旧文件。

H01 等 ID 分配后保持稳定；排序变化不重新编号。slug 使用简短、可读的字母或数字与连字符。文件之间使用相对链接。用户指定输出目录或已有兼容结构时沿用，不另建重复材料。

## index.md

维护以下信息，格式可根据已有文档调整：

- **项目上下文**：项目路径、业务摘要、识别出的技术栈、简要模块和链路地图。
- **分析快照**：日期、仓库版本（可取得时）、已查看范围及覆盖限制；只在相关时标注本地未提交变更。
- **当前状态**：当前阶段、已选 ID、已完成事项、待处理事项、当前一个待回答问题。用户回答后及时更新。
- **候选表**：ID、名称、业务问题、核心机制、关键证据、技术深度与可讲性、证据缺口、推荐理由、状态及材料链接。

阶段使用清晰状态，例如：待选择、待深挖、访谈中、素材草稿、素材已生成、证据需复查。状态表示当前进度，不是完成度评分。

## analysis.md

每个选定亮点保存：

1. 一句话技术价值与业务背景。
2. 从输入到结果的调用链及关键状态变化。
3. 核心机制、成立前提和约束范围。
4. 相关异常、并发、重试和恢复边界。
5. 合理替代方案、取舍、限制及遗留问题。
6. 测试与结果、缺证及最小验证方案。
7. 证据清单与每个重要结论的状态。

给证据分配局部稳定 ID，如 E01。标明来源类型：源码、测试定义、测试输出、文档、变更记录、用户陈述、推测。引用尽量包含相对文件路径、类或函数、当前行号或范围及相关版本。

对未证实结论写清“为什么这样推测”和“如何验证”，对发现的反例明确记录。源码变更导致结论失效时标记该结论和依赖它的简历主张，保留仍有效的部分。

## interview.md

记录以下信息，已有回答不重复问：

- 个人负责的范围及与团队的协作边界。
- 用户实际做过的调查、决策、实现、复现、测试或改进。
- 原有方案、变更前后区别、具体难点和取舍。
- 已确认结果、测量条件、交付状态及可用证据。
- 逐项回答，编号如 Q01；注明用户陈述或引用证据。
- 尚未解决的事实缺口，以及当前一个待回答问题。

按对最终表述影响最大的未知项提问。选择题提供推荐选择及理由；事实题提供回忆线索或推荐表达结构，不替用户填经历或数字。

如果用户明确表示未参与该亮点实现，或无法解释其基本设计，停止针对个人贡献的追问，直接写完整的“项目 Owner 视角 STAR”。按 Owner 的视角描述业务背景（S）、项目目标与责任（T）、项目层面的设计、决策与协作（A）、可证实的交付结果（R）；使用第一人称时应标明这是角色视角复盘，不是用户个人经历。不要要求用户先复现或补课，也不要把 Owner 的行动直接变成用户简历中的个人成就。

若用户只回答某一项“不记得”“没有指标”或跳过，不推断其未参与整个亮点；只记录该事实缺口，并在仍有基础时继续问其他具体行动。用户明确表示未参与或不懂后，则不再就个人行动追问。

## resume.md

依材料充分程度注明“素材草稿”或“素材已生成”，保存：

### STAR 事实稿

- **S**：业务场景、原有问题与约束。
- **T**：个人目标和职责边界，来源于已确认材料。
- **A**：个人调查、判断、实现或验证步骤及取舍。
- **R**：可确认的交付或验证结果，必要时附适用条件。

用户的个人参与和行动已确认时，以上 STAR 按真实职责填写。用户明确未参与或无法解释设计时，仍生成 STAR，但切换到项目 Owner 视角：T 说明 Owner 对项目结果负责的目标，A 说明代码证据支持的项目决策与设计行动，R 仅写已证实的结果。此稿属于角色视角的项目复盘，不能标为用户亲历或直接作为用户的简历经历。

Owner 视角稿使用完整 S/T/A/R 结构，不用简短项目介绍替代。表达可以连贯、适合口头讲述，但每项都须与项目证据相符；原作者意图无法证实时，将 Owner 决策理由标为分析性重构。

### 简历候选表述

每个适用亮点提供 1～2 个候选版本。个人经历版本集中在有证据的问题、个人行动与结果；没有指标时使用确切的交付、测试、验收或修复结果。Owner 视角 STAR 单独标注为“项目 Owner 视角/项目复盘”，用于项目讲解和面试准备，不直接充当用户的个人简历经历。

完整 STAR 缺关键事实时提供部分素材和缺口，不输出貌似完整的个人经历。成稿不包含占位数字、未经支持的规模，以及暗示未发生结果的词语。

### 主张与证据映射

| 主张 | 证据或回答 ID | 支持范围与限制 |
| --- | --- | --- |

对所有候选表述的关键事实给出来源，允许引用用户已经确认的经历；不要把这类回答错误标为源码证明。

### 待补材料

列出会提高表述可信度或具体程度的少量材料，以及获得它们的下一步。个人资料、指标或验证缺失时在这里说明，不让占位内容进入可直接使用的简历版本。

## 更新规则

续接时先读当前索引和相关亮点，局部更新。保留用户编辑与稳定编号；用户修改与已有结论冲突时只核查相关事实。阶段完成或等待用户时保存当前进度，避免依赖聊天上下文作为唯一记录。

写入后读回相关文件，确认相对链接存在、状态一致、主张能够追溯。无需为材料创建额外数据库、状态 JSON、安装说明或独立测试脚本。

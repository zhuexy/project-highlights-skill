# 持久化材料约定

## 文件组织

默认把材料存放在目标仓库之外的用户级 Codex 数据目录：优先 `$CODEX_HOME/project-highlights/<project-id>/`，未设置 `CODEX_HOME` 时使用 `$HOME/.codex/project-highlights/<project-id>/`；Windows 使用用户 profile 下的 `.codex`。

稳定的 `project-id` 使用 `<repo-slug>-<hash>`：`repo-slug` 用于识别项目，`hash` 是规范化项目身份字符串的 SHA-256 前 12 位。身份字符串优先取 Git remote；GitHub 的 SSH 与 HTTPS 形式需归一成相同的 `github.com/owner/repo`，并去除 `.git` 后缀与尾部斜线。其他 remote 统一主机名大小写并去除 `.git` 后缀与尾部斜线。没有 remote 时，使用规范化仓库根目录的绝对路径；Windows 路径比较时忽略大小写并统一分隔符。索引记录该身份字符串、标识和来源。

按需要创建以下文件：

```text
<user-codex-home>/project-highlights/<project-id>/
  index.md
  H01-payment-callback/
    analysis.md
    resume.md
```

上面是组织示例，目录名要与实际候选对应。发现阶段创建或更新索引；为候选生成 Owner 视角 STAR 时按需要创建分析目录和素材文件。不要提前创建空文件或虚构示例亮点。用户明确指定其他输出目录时遵从。

索引至少记录规范化仓库根路径、Git remote（若有）、规范化项目身份字符串、项目标识和标识来源。续接时用相同规则重算 ID；remote 改变但仓库根路径一致时，检查已有索引中的根路径以找到并续接旧材料，而不是另起一份。不要仅按仓库名匹配。

旧版本可能在仓库根目录创建了 `project-highlights/`。可以读取旧索引以续接上下文，但后续写入默认的用户级目录；不自动删除、覆盖或移动旧文件。

H01 等 ID 分配后保持稳定；排序变化不重新编号。slug 使用简短、可读的字母或数字与连字符。文件之间使用相对链接。用户指定输出目录或已有兼容结构时沿用，不另建重复材料。

## index.md

维护以下信息，格式可根据已有文档调整：

- **项目上下文**：项目路径、业务摘要、识别出的技术栈、简要模块和链路地图。
- **分析快照**：日期、仓库版本（可取得时）、已查看范围及覆盖限制；只在相关时标注本地未提交变更。
- **当前状态**：当前阶段、重点 ID、已完成事项、待处理事项。
- **候选表**：ID、名称、类型（技术/业务/复合）、业务问题、核心机制、关键证据、价值与可讲性、证据缺口、实验/验证建议摘要、推荐理由、Owner STAR 摘要、状态及材料链接。

阶段使用清晰状态，例如：待深挖、素材草稿、素材已生成、证据需复查。状态表示当前进度，不是完成度评分。

## analysis.md

每个选定亮点保存：

1. 一句话技术价值与业务背景。
2. 从输入到结果的调用链及关键状态变化。
3. 核心机制、成立前提和约束范围。
4. 相关异常、并发、重试和恢复边界。
5. 合理替代方案、取舍、限制及遗留问题。
6. 测试与结果、缺证及最小验证方案。
7. 证据清单与每个重要结论的状态。
8. 每个待验证主张的实验/验证指导：假设、环境与样本、基线/对照、步骤、主指标和护栏指标、判定方式、局限及状态（建议，尚未执行）。

给证据分配局部稳定 ID，如 E01。标明来源类型：源码、测试定义、测试输出、文档、变更记录、用户陈述、推测。引用尽量包含相对文件路径、类或函数、当前行号或范围及相关版本。

对未证实结论写清“为什么这样推测”和“如何验证”，对发现的反例明确记录。源码变更导致结论失效时标记该结论和依赖它的简历主张，保留仍有效的部分。

## resume.md

依材料充分程度注明“素材草稿”或“素材已生成”，保存：

### 项目 Owner 视角 STAR

- **S**：业务场景、原有问题与约束。
- **T**：项目目标；目标若由设计推断，标注为 Owner 视角重构。
- **A**：代码和材料支持的项目设计、机制与取舍；动机若无法确认，标注为推断。
- **R**：可确认的交付或验证结果，必要时附适用条件。

默认使用完整 S/T/A/R 结构，明确这是项目角色视角复盘，不自动代表用户的真实职务或亲历行动。表达可以连贯、适合口头讲述；原作者意图无法证实时，将 Owner 决策理由标为分析性重构。

### 简历候选表述

每个适用亮点提供 1～2 个候选版本。突出有证据的问题、机制、业务能力和已确认结果；没有指标时使用确切的实现或交付结果。Owner 视角内容标注为“项目 Owner 视角/项目复盘”。

完整 STAR 缺关键事实时提供部分素材和缺口，不把目标或假设包装成已实现结果。成稿不包含占位数字、未经支持的规模，以及暗示未发生结果的词语。

### 主张与证据映射

| 主张 | 证据或回答 ID | 支持范围与限制 |
| --- | --- | --- |

对所有候选表述的关键事实给出来源，区分源码、测试、实验、验收、生产观察和分析推断。

### 待补材料

每个待验证主张后紧跟实验/验证建议，至少说明要验证的假设、如何建立可比的基线或对照、具体操作、如何采集量化指标、什么结果支持/不支持主张，以及主要局限。注明方案尚未执行。缺少基线、流量、波动或业务口径时，列出所需信息并给出获取方式；不编造固定阈值、样本量或结果。

## 更新规则

续接时先读当前索引和相关亮点，局部更新。保留用户编辑与稳定编号；用户修改与已有结论冲突时只核查相关事实。阶段完成或等待用户时保存当前进度，避免依赖聊天上下文作为唯一记录。

写入后读回相关文件，确认相对链接存在、状态一致、主张能够追溯。无需为材料创建额外数据库、状态 JSON、安装说明或独立测试脚本。
